## What this step builds
A script hook that prints output and exits 0 currently has that output **thrown away**. `ScriptHook::EXIT_ALLOW` returns `HookResult::allow($output)` (`ScriptHook.php:642`) — the stdout is carried in the result's message — but `HookRegistry::executeHooks()` ends `return $modified ?? $inertRewrite ?? HookResult::allow();` (`HookRegistry.php:428`), rebuilding a permitting verdict with an **empty** message. `ScriptHook.php:631-641` documents this verbatim: on the live path it "goes NOWHERE".

This step adds a dedicated **`additionalContext`** field to `HookResult` (distinct from `message`, which is the human/deny reason; distinct from `modifiedInput`, which is JSON **tool arguments**) and makes that context survive all the way to the model on **both** tool-result paths.

## SUPERVISOR RULINGS (2026-09-06) — binding, do not re-litigate
- **R-1 (consumer scope): "Wire BOTH Runtime and Chat."** P7.S1 must make `additionalContext` genuinely READ on the live path — not a producer-only dead field (which §1.10 forbids). Both model-visible tool-result paths (`Runtime::settle()` and `Chat::applyPostToolUse()`) must append the context. **This explicitly clears the `src/Chat.php` collision row for P7.S1** (plan §5 stop-and-ask; the supervisor answered it on 2026-09-06). Record the clearance in the commit message and worklog exactly as P6.S3 recorded its Chat.php touch.
- **R-2 (overflow mechanism): "New retained-file path."** Implement a purpose-built retained-overflow file (0600 via umask-narrowing + atomic `rename`, like `Support\ToolIpcFiles::write()`) that is **NOT** discarded after read and whose lifetime is tied to the session/tool-result, **not** the `STALE_AFTER_SECONDS = 3600` IPC sweep. The plan's "spillover to a file plus a preview" requirement stands.

## ORCHESTRATOR RULING — units
- **R-3 (units): the cap is BYTES, 10,000 bytes.** The plan text says "10,000 characters", but every bound in this subsystem is byte-denominated (`TruncatesOutput` caps 65536/16384/120 bytes; `ScriptHook::clip()` at `ScriptHook.php:863-865` states byte-boundary cutting "deliberately — this is arbitrary program output, not guaranteed UTF-8"). Cut with `mb_strcut(..., 'UTF-8')` per the `TruncatesOutput` idiom, expose the cap as a named `public const` in BYTES (e.g. `MAX_ADDITIONAL_CONTEXT_BYTES = 10000`), and state in the doc-comment that the plan said "characters" and why bytes is used. Use the trait's `max(1, …)` guard idiom, NOT the `$maxBytes <= 0` "no cap" sentinel unguarded (`TruncatesOutput.php:141-142,367-379` record that misusing that sentinel silently disabled the bound twice — Glob returned 1,091,833 bytes against a 65,536 cap).
