# prompt_kit/CONTEXT.md — accumulated project context, harness-portable

**What this is.** Forty-four pieces of accumulated context about this repository that had been
living in Claude Code's per-project memory store
(`~/.claude/projects/-home-sites-sugarcraft/memory/`). That store is **specific to one harness on
one machine**: OpenCode cannot see it, a different checkout cannot see it, and nothing in the repo
referenced it. This file exists so that switching harness — or losing that directory — costs
nothing.

**Provenance.** Generated mechanically from the memory files, bodies **verbatim**, nothing
summarised and nothing dropped. Each entry keeps its original slug, so a `[[link]]` between
entries still resolves by searching this file for the slug. The originals remain where they were;
this is a copy, not a move, and it goes stale if they are updated without regenerating.

**The generator is fail-closed, and it had to be made so.** The first version of this file was
generated by a script that read each entry's `type` with an unanchored `type:\s*(\S+)` — which
matches `node_type: memory` on the line *above* the real `type:` field. Every one of the 44 entries
was therefore classified `memory`, fell outside the grouping table, and was **silently dropped**:
the output was a plausible-looking 17 KB file containing this header and essentially nothing else.
It was caught only because 17 KB was checked against an expected ~224 KB. The regenerator now
anchors the field to its own line **and asserts that every input file appears in the output**, so
the same class of failure aborts instead of shipping. That is the lesson twice over — the tree this
file belongs to has a standing rule that a scanner answering the same way for every input reads as
working, and it applied to the scanner that wrote this sentence.

**How to read them.** These record what was true **when they were written**. Several are marked
resolved, superseded or corrected in their own text. **If an entry names a file, function, line
number or flag, verify it still exists before acting on it.** That is not decoration: one of these
entries is itself a correction of an earlier one that was wrong, and the plan this repo is
currently executing has caught stale `file:line` citations in its own documents five times.

**Relationship to the other documents.** `prompt_plan.md` is the operating manual for the
prompt-architecture plan, `prompt_worklog.md` its append-only record, `prompt_resume.md` the entry
point saying where the plan is now. This file is none of those — it is background about the
repository that predates and outlives that plan. Where they overlap, the plan documents are
authoritative and more current.

## `llm-request-timeouts`

*LLM completion HTTP calls need a short connect_timeout but never a blanket total-request timeout — completions can legitimately run tens of minutes on a slow/loaded server*

<sub>originally `feedback_llm_request_timeouts.md`, type `feedback`</sub>

When recommending or adding timeouts to provider/LLM HTTP clients (Guzzle or otherwise), distinguish `connect_timeout` from the overall request `timeout`. A short `connect_timeout` (10-30s) is correct — it fails fast when a host is genuinely unreachable. A blanket total-request `timeout` copied from a short-lived call pattern (e.g. sugar-crush's MCP client's `timeout => 30`) is wrong for LLM completions — a real, in-progress completion can legitimately take tens of minutes on a loaded or slow/remote server, so a flat 30s ceiling would abort legitimate work, not just hung requests.

**Why:** user correction during the crush_code.md sugar-crush audit (2026-08-13): "requests can take 30 minuts easily if on a laggd srver th timeout suggestd is way too low .. maybe a connect timeout of 30 but not a timout of 30." The plan had recommended copying `src/MCP/McpClient.php`'s `timeout => 30` onto the LLM provider clients — correct for MCP's short tool calls, wrong for completions.

**How to apply:** any time a plan/fix proposes adding an HTTP timeout to an LLM-completion code path, propose only a short connect-timeout, and explicitly call out that the overall request timeout must stay high/unset — don't reuse a timeout value from a different, shorter-lived call type without checking whether the target call can legitimately run long.

## `packagist-not-path-repos`

*"Sibling deps resolve from Packagist; per-lib manifests carry NO repositories[] block and CI injects path repos at build time (landed 2fa678a7, docs now agree)"*

<sub>originally `feedback_packagist_not_path_repos.md`, type `feedback`</sub>

When wiring a new `sugarcraft/<dep>` into a lib's `composer.json`, add ONLY the
plain `require` entry. Per-lib manifests carry **no `repositories[]` block at
all** — as of `2fa678a7` all 394 sibling path-repo entries were stripped from 53
manifests and the checked-in docs (CLAUDE.md, AGENTS.md, CONTRIBUTING.md, and the
`path-repo-closure` skill) were rewritten to match, so the old contradiction is
gone.

**Why:** the user's reasoning, verified by probe — each `<lib>/` is published
standalone as `sugarcraft/<lib>`, and a `../<dep>` path repo is a **hard fatal**
(`PathRepository.php`: "The url supplied for the path … does not exist", exit 1)
for anyone cloning the split repo. It was invisible to normal consumers because
Composer honours `repositories` only on the ROOT package and ignores a
dependency's entirely — probed both directions. All 58 libs are published, so
plain requires resolve.

**How to apply:**
- New dep = one edit, the `require` line. Verify with
  `php tools/check-path-repos.php --no-lib-path-repos` (the committed-tree guard).
- `--fix --strict-closure` is now a **build** step, not an authoring step. CI runs
  it before every `composer install` (9 sites in `ci.yml`/`pty-matrix.yml`/`vhs.yml`)
  so a PR's own sibling code is what gets tested. Locally, inject, test, then
  `git checkout -- '*/composer.json'`. **Never commit the injected entries.**
- `--strict-closure` reporting ~394 gaps on the committed tree is BY DESIGN now,
  not drift.
- **Never commit a per-lib `composer.lock`** (`/*/composer.lock` is gitignored;
  the root keeps its own). A stale lock makes `composer install` resolve from the
  lock and *silently ignore* the injection — it only warns and exits 0, so CI
  would look green while testing published siblings. This is why the 14 tracked
  locks were untracked in the same commit.
- The **root** manifest is the exception and keeps a full path-repo closure — the
  root IS the directory those `../` urls resolve against. `3bc5d269` completed it
  (candy-focus had a stale `vcs` entry, sugar-gallery none).

Related: [[reference_monorepo]], [[project_splitsh_not_equal_git_subtree]],
[[project_stale_vendor_false_test_failures]].


## `feedback-phpunit-kill-pattern`

*"When PHPUnit may hang (PTY/FFI/proc_open tests), don't rely on `timeout`; launch a backgrounded killer process and pkill phpunit/timeout/php"*

<sub>originally `feedback_phpunit_kill_pattern.md`, type `feedback`</sub>

When running PHPUnit suites that touch PTYs / FFI / proc_open (e.g. candy-pty, candy-wish), `timeout 30 vendor/bin/phpunit ...` is NOT reliable — the process can wedge in a state where SIGTERM doesn't tear it down and the harness blocks indefinitely.

**Why:** PTY master/slave fds + FFI handles + zombie child procs leave PHP unable to honor a top-level SIGTERM cleanly. The `timeout` wrapper itself may also hang.

**How to apply:** instead of `timeout N <cmd>`, run a background sentinel that hard-kills the family by name after the window:

```bash
( sleep 30 && pkill -9 -f 'vendor/bin/phpunit' ; pkill -9 -f '/bin/sh -c.*phpunit' ; pkill -9 timeout ; pkill -9 -f 'runchild.php' ) &
WATCHDOG=$!
cd <slug> && vendor/bin/phpunit <args> 2>&1 | tee /tmp/phpunit.out
kill $WATCHDOG 2>/dev/null
```

Or even simpler: spawn the run with `run_in_background: true`, then a second `Bash` call that does `sleep 30 && pkill -9 -f phpunit` also `run_in_background`. Read the captured output file after.

Related: [[project_candy_wish_pty_dual_mode]].

## `feedback_workflow_commit_per_step`

*"Multi-agent build workflows must commit after every step; parallel tracks sharing one uncommitted tree makes every reviewer flag every other step's diff"*

<sub>originally `feedback_workflow_commit_per_step.md`, type `feedback`</sub>

When orchestrating a multi-step build via the Workflow tool where each step has its own review agent, **commit each step before the next one starts**. Do not run parallel tracks that all write into one shared, uncommitted working tree.

**Why:** in the first sugar-crush Wave 1 run (2026-08-10), 7 tracks ran concurrently with no commits until the end. Every reviewer ran `git diff` and saw all 16 steps' work at once, so nearly every review returned a traceability blocker along the lines of "this diff bundles unrelated work from five other steps and cannot be committed as just this step." Those BLOCKED verdicts were artifacts of the harness design, not code defects — the code was fine and the suite was green. It also made the results genuinely hard to untangle afterward: shared files (`Message.php`, `EngineBackend.php`, `Bootstrap.php`) carried several steps' changes at once and could not be split into per-step commits without hand-editing.

**How to apply:** structure the workflow as strictly serial steps — Build → Review → Fix (capped) → **Commit** — with a dedicated commit agent per step. Have commit agents commit only; the supervisor pushes once at the end (keeps push races impossible and keeps the supervisor in control of what reaches the remote). If parallelism is needed for speed, tracks must be file-disjoint *and* each still commit per step. Tell reviewers the tree was clean before the step so everything uncommitted is that step's own work.

<sub>originally `project_ansi_to_style_conversion.md`, type `project`</sub>

## `project-ci-matrix-and-pr-path-repo-gotchas`

*"Two non-obvious SugarCraft CI behaviors — empty-matrix run failure shape, and why force-all PRs go all-red while master is green"*

<sub>originally `project_ci_matrix_and_pr_path_repo_gotchas.md`, type `project`</sub>

Two SugarCraft `.github/workflows/ci.yml` behaviors that look like bugs but trace to known causes (both confirmed 2026-06-01):

**1. Empty matrix must be `{include:[]}`, not `{php:[],lib:[]}`.**
`scripts/affected-libs.php::php_lib_matrix()` builds the per-job matrices. On narrow change-sets phpstan/macos resolve to zero libs. An empty matrix *dimension* (`php: []`) is a hard Actions error ("Matrix vector 'php' does not contain any values") → the job aborts at setup and the **whole run is marked failure even though every job that ran was green** (seen: 44/44 jobs success, run=failure, `phpstan=0/mac=0`). Fix shipped: emit `{include: []}` for the empty case (zero cells, zero check_runs, no error). Don't revert to empty dimensions. **Practical (re-confirmed 2026-06-03 on sugar-reel pushes): a narrow single-lib master push STILL shows run=failure even with the fix, on every push (pure-docs pushes too). To verify, spot-check the per-lib check-runs, not the run conclusion — `unset GITHUB_TOKEN && gh api repos/detain/sugarcraft/commits/<merge-sha>/check-runs --jq '.check_runs[]|select(.name|test("<lib>|Path-repo"))|"\(.conclusion//.status)\t\(.name)"'` → want `Test PHP 8.3/8.4 · <lib>`, `Coverage · <lib>`, `Path-repo closure`, `render (<lib>)` = success. Do NOT loop-poll the run to completion; one spot-check is enough.**

**2. Force-all PRs go ALL-red; master pushes are green — this is expected, not a regression.**
Per-lib jobs run `cd <lib> && composer install` with no lock, against `../<dep>` path repos. On a **PR**, `actions/checkout` lands on a detached merge ref, so each path repo reports its version as `dev-<sha>` instead of `dev-master` → the `dev-master` constraint can't resolve → "Your requirements could not be resolved" on every per-lib job. On a **master push** the checkout is the `master` branch, path repos report `dev-master`, everything resolves. So: **verify CI on the post-merge master run, not on the PR.** A force-all PR (one that touches `composer.json`/`composer.lock`, `ci.yml`, or `scripts/affected-libs.php`) will show dozens of red per-lib jobs purely from this — it does not mean the change is broken. This path-repo `dev-master` resolution gap on PRs is unfixed (would need branch-alias in every composer.json or a branch checkout). Relates to [[reference_monorepo]] and [[project_stale_vendor_false_test_failures]].

## `project-grep-is-ugrep-in-agent-shells`

*"A bare `grep` in a Bash-tool shell is a function shadowing GNU grep with ugrep; the real hazard is that recursive scans honour .gitignore, so an absence census silently skips vendor/ and ignored files"*

<sub>originally `project_grep_is_ugrep_in_agent_shells.md`, type `project`</sub>

On this machine, `type -a grep` in a Bash-tool shell reports **`grep is a function`**
before `/usr/bin/grep`. The harness installs a shell function routing `grep` to
**ugrep** via the `claude` binary.

**THE HEADLINE THIS MEMORY ORIGINALLY CARRIED WAS WRONG, and was corrected by
measurement (SugarCraft round 56, backlog E516, ugrep 7.8.4 vs GNU grep 3.11).**

- WHAT IT SAID: "`grep -qv` silently always answers no."
- WHAT IS TRUE: `grep -qv X` under the shim behaves as `! grep -q X` — the `-q`
  decision is taken on the PATTERN and `-v` is ignored for exit status. So it answers
  *no* exactly when the pattern IS present, and *yes* when it is absent. `-lv`/`-Lv`
  diverge the same way. Still a real divergence, still worth avoiding, but it is not
  a constant.
- WHY THIS STILL MATTERS: the idiom is unreliable either way. Use `! grep -q` or
  `/usr/bin/grep`.

**THE DIVERGENCE THAT ACTUALLY BITES is recursive scanning.** The shim passes
`--ignore-files`, so **it honours `.gitignore`**. Measured: in a scratch repo with an
`ignored/` directory, `grep -rn NEEDLE .` found **1 of 2** occurrences and `grep -rc`
reported only the tracked file; GNU found both. In this repo that silently excludes
every `vendor/` tree and every per-lib `composer.lock`.

**So the operative rule is not "never write `grep -qv`" — it is "an agent-shell
`grep -r` cannot see ignored files".** Any census whose answer is load-bearing (an
absence assertion, a count you will write down) must call `/usr/bin/grep` by absolute
path.

**Bounded by measurement:** counts on a NAMED file agree between the two. The function
is **not exported** (no `BASH_FUNC_grep` in the environment), so `#!/bin/bash` script
files, `bash -c`, CI steps and shell-outs from PHP all get real GNU grep — only inline
agent commands are shadowed. `git grep` is git's own and unaffected.

**And the control must be able to fail.** The first control written for this was
`/usr/bin/grep -qv x /dev/null`, which reported FAILED — the grep was fine, an empty
file has no line an inverted match can select, so it could never pass. Assert a known
positive AND a known negative.

Recorded in the SugarCraft backlog as E457 (original, headline wrong) and **E516**
(the correction — cite this one). See [[feedback-delegate-verification]].


## `project_image_marker_zone_sentinel_collision`

*candy-core image markers and candy-mouse zone sentinels both start at U+E000 — combining them silently kills every mouse zone after the first image*

<sub>originally `project_image_marker_zone_sentinel_collision.md`, type `project`</sub>

`candy-core`'s `ImageOverlay::MARKER_BASE` is `0xE000` and an image marker cell is `MARKER_BASE + id` with ids handed out from 0. `candy-mouse`'s `Sentinel::OPEN` is `"\xEE\x80\x80"` — literally U+E000. So the **first image in a frame emits a byte-identical copy of an opening zone sentinel**; `Scanner` then reads the rest of the frame as one unterminated zone and drops every zone after it. Every click target below the image goes dead.

Reproduce:
```php
$m = new Mark();
$s = Scanner::new(); $s->scan($m->wrap('tab1','A')."\u{E000}".$m->wrap('tab2','B'), 80);
count($s->all()); // 1, not 2 — tab2 is gone
```

**Why:** neither library is wrong alone; the collision only exists in a lib that uses both. sugar-crush hit it when the image-rendering and mouse-zone features merged (fixed in `c5e925c9`).

**How to apply:** mask the PUA block (`U+E000`–`U+F8FF`) out of the copy the **scanner** reads, never the copy sent to the terminal — the real markers still have to reach `Program` to be resolved into paints. Match well-formed sentinel triples first in the alternation so genuine markup survives, and replace other PUA cells with a single space (width-1 → width-1) so zone column arithmetic is unchanged. See `Renderer::maskImageMarkers()` and `tests/ImageMarkerZoneCollisionTest.php`. Any new rendered glyph must stay outside that block. Related: [[project_tui_render_invariants]].


## `opencode-task-vs-delegate-routing`

*"OpenCode routes agent spawns through task (write-capable) vs delegate (read-only) tools based on the target agent's permission profile — using the wrong one fails immediately with a routing error"*

<sub>originally `project_opencode_task_vs_delegate_routing.md`, type `project`</sub>

OpenCode classifies a custom agent as read-only if its permission profile has `edit: "deny"`, `write: "deny"`, AND `bash` whose top-level wildcard (`bash["*"]`) is `"deny"` — even if specific command overrides inside that bash object are `"allow"`. Read-only agents must be spawned via the **`delegate`** tool; write-capable agents (anything with `edit`/`write` allowed, or `bash["*"]: "allow"`) must be spawned via **`task`**. Calling `task` on a read-only-classified agent fails immediately with: "Agent 'X' is read-only and should use the delegate tool."

**Why:** Discovered live during the first bootstrap run of the sugar-crush orchestration plan (`crush_code_plan.md`, "Execution Protocol for Orchestrated Implementation"). `sugarcrush-committer` was originally configured like `sugarcrush-reviewer` — `bash: {"*": "deny", "git add *": "allow", "git commit *": "allow", ...}` — which got it classified read-only despite needing to actually mutate git state. `delegate` still runs whatever commands an agent's bash allowlist permits; the tool choice is purely about spawn routing (write-capable agents get more careful/sequential handling), not an additional restriction on top of the permission block.

**Fix pattern:** For an agent that genuinely needs to write/commit but should stay narrowly scoped, flip the bash default to `"*": "allow"` with the *dangerous* operations explicitly denied (`git push --force*`, `git reset*`, `git checkout --*`, `git clean*`, `git add -A`/`.`, `git commit --amend*`), rather than `"*": "deny"` with only safe operations allowlisted. This gets it correctly classified write-capable (spawn via `task`) while still hard-blocking the destructive commands at the permission layer — see `sugarcrush-committer`'s block in `.opencode/opencode.jsonc`.

**How to apply:** Whenever adding a new custom OpenCode agent to this repo that needs `bash` access but should stay restricted, decide up front whether it's conceptually read-only (→ `bash: {"*": "deny", <allowlist>}`, spawn via `delegate`, e.g. `sugarcrush-reviewer`/`reviewer`/`explore`) or conceptually write-capable-but-guarded (→ `bash: {"*": "allow", <denylist of dangerous ops>}`, spawn via `task`, e.g. `sugarcrush-committer`). Don't try to allowlist a write-capable agent's commands the same way a read-only agent's are allowlisted — it will silently misclassify and every spawn will fail at the routing layer before the agent's own prompt even matters. See [[project_sugarcrush_orchestration_plan]] for the full plan this agent set implements.

## `stale-vendor-false-test-failures`

*A bare composer update de-symlinks vendor/sugarcraft into Packagist copies and silently voids suite figures; "closure intact" is a PER-LIB fact, strict-closure walks require only, and ls lies — verify with PHP is_link plus a content md5*

<sub>originally `project_stale_vendor_false_test_failures.md`, type `project`</sub>

Each lib has its own `vendor/` + `composer.lock`. Siblings resolve from **Packagist** by default; local `../<dep>` path repos are **injected at build time** and never committed. Two opposite failure modes, and the fix for one causes the other.

**Stale direction:** a lib's local `vendor`/`composer.lock` pins a pre-change snapshot of a sibling — spurious `Class "…" not found` for a class that exists in the sibling's source.

**The dangerous direction, because it is SILENT:** a bare `composer install`/`composer update` **replaces `vendor/sugarcraft/*` symlinks with real Packagist copies**. The suite still passes, still prints a total, and is **no longer testing the working tree**. Measured 2026-08-22: it voided two full sugar-crush runs and a 14-lib sibling sweep in one session — the fix under test was never loaded.

**"The closure is intact" is a PER-LIB fact, not a repo-wide one.** After sugar-crush was restored to 18/18 and verified, a 16-lib sibling sweep came back **all rc 0** while **nine** libs still vendored a stale `candy-core` (`Width.php` md5 `f2a3558f…`/33,275 B vs the worktree's `270fc3f2…`/38,125 B). Only 4 of 16 were signal. ⚠️ **The oft-cited `candy-buffer` "1,621 → 1,661" proof is NOISE — do not reuse it.** Measured 2026-08-22 on one clean correctly-linked tree, three runs gave 1569 / 1545 / 1507 assertions (spread 62 > the +40 treated as signal); `candy-buffer/tests/BufferTest.php` uses `rand()`. Its TEST count (274) is stable; its assertion count measures nothing. The conclusion still holds — `--fix --strict-closure` really does inject zero repos for `candy-buffer` — but verify that by reading the manifest after `--fix`, never by a suite delta. **The sugar-crush skip-count alarm (1 → 2, `GitignoreAwarenessTest::testTheMonorepoPathRepoSymlinksAreNotFollowed`) has NO sibling equivalent**, so siblings must be checked by content, per lib.

**How to apply:** never trust a figure taken after a bare `composer update`. Round-trip: `php tools/check-path-repos.php --fix --strict-closure` → `composer update` in each affected lib → `git checkout -- '*/composer.json'` (never commit) → `php tools/check-path-repos.php --no-lib-path-repos` must exit 0 → **re-measure everything taken since**. ⚠️ **`--fix --strict-closure` walks `require`, NOT `require-dev`** — `candy-buffer` holds `sugarcraft/candy-core` in require-dev and survives the whole repair; it needs a hand-injected scratch `repositories[]`, its own `composer update`, then `git checkout --` of that one manifest. ⚠️ **The content probe is only meaningful on a file the round ACTUALLY CHANGED.** Measured 2026-08-22 with `symlinks=0/18` — closure entirely absent — a probe on `candy-sprinkles/src/Style.php` printed `SAME`, because that round touched only `StyleTest.php`; an unchanged file is byte-identical in the Packagist copy by construction. **`is_link()` is primary and cannot be fooled; content is secondary.** Pick the probe file out of the round's own diff. Also re-check **third-party drift** (compare `composer.lock` versions against any lane copies) after a user-run update — a bump between trees silently invalidates delta arithmetic; measured zero that time. Detect with PHP plus a content hash, never `ls` (`ls -l | grep -c '^l'` printed a correct-looking 18 twice while every entry was a directory): `php -r 'var_dump(is_link($p));'` and compare `md5_file()` of the vendored file against the live tree's. ## `project-sugarcrush-async-and-double-diff`

*"sugar-crush architecture facts learned fixing the async-completion freeze, a double-diffing render corruption bug, and tool-call visibility — read before touching Chat.php/EngineBackend.php/Renderer.php again."*

<sub>originally `project_sugarcrush_async_and_double_diff.md`, type `project`</sub>

**Async completion (PR #1400).** `EngineBackend::completeAsync()` used to wrap a fully blocking `complete()` call in `new React\Promise\Promise($executor)` — but a Promise executor runs *immediately*, not deferred, so the whole TUI froze (no spinner, no keystrokes, no Ctrl+C) for every provider round-trip. Fixed by forking the real work into a child process; the parent only watches a non-blocking socket via `Loop::addReadStream()`. Same fix pattern reused for tool calls (see below) and gated by a `Backend\CancellationToken` threaded through `Backend::completeAsync()`'s new 3rd param, polled every 100ms, killing the child on Escape-Escape abort.

**Double-diffing render corruption (PR #1402, 2nd commit).** `Chat::view()` used to compute its own cell-level diff (`Buffer`/`DiffEncoder`) and return only changed bytes as an optimization — but `bin/sugarcrush` drives it through a plain `candy-core\Program`, whose own `Renderer` *also* diffs whatever `view()` returns, line-by-line, against the previous call's return value. Chat's pre-diffed cursor-jump escape bytes were never literal display text, so Program was diffing one diff's raw bytes against another diff's raw bytes as if they were screen content — producing cursor placement with no relationship to the actual frame (symptom: typed text/replies appearing in the wrong row, e.g. the status bar, once a conversation grew past one frame). Fix: `view()` now always returns the full literal frame; **candy-core itself was not touched** — its Renderer's diffing is correct and is the only diffing layer that should exist. Removed now-dead `previousFrame`/`prevHeight`/`prevWidth`/`width` fields and `bufferFromOutput()`/`resetPreviousFrame()` (zero external callers).

**Tool-call visibility (PR #1402, 3rd commit).** Two separate bugs made tool calls look silent: (1) `Message::withToolResults()` discarded both the passed-in `ToolResult[]` AND the message's own content, always producing a blank assistant bubble — not just "no marker," actual content loss; (2) tool execution was fully synchronous within one `update()` call, so there was no visible "running" state before a (possibly slow) tool finished. Fixed via `Message::toolRunning()` (a placeholder tagged with `pendingToolCallId`, replaced later by matching id) plus `Chat::beginToolCalls()`/`finishToolCalls()`/`ToolResultsMsg`, which **always forks every tool call now** (previously only forked for 2+ calls with a pool configured) and waits non-blockingly via `waitForToolChildrenAsync()` (periodic-timer WNOHANG poll, same non-blocking rationale as the completion fix). `handleToolCalls()`/`executeToolsSequentially()`/`executeToolsParallel()`/blocking `waitForToolChildren()` are gone — replaced, not kept alongside.

**Global `Loop::get()` test hygiene gotcha (found chasing a "flaky" test).** `StreamingCommandBackend::completeAsync()` called `Loop::stop()` unconditionally in a `finally` block — a real production bug (would kill a whole running Program's event loop on its first reply if that backend were ever configured), not just a test artifact. Its own test never drove the loop to resolve the promise it returned, leaving a stale `Loop::futureTick()` callback (containing that `stop()` call) permanently queued on the **shared global `Loop::get()` singleton**, which fired during a later, completely unrelated test's `run()` call and stopped it prematurely. Lesson: any test that calls `completeAsync()`/registers timers on `Loop::get()` MUST drive it to actual resolution (or otherwise drain the queue) before finishing, or it corrupts whichever later test next calls `Loop::get()->run()` — regardless of test file. See `[[project_sugarcrush_guzzle_baseurl_bug]]` for the unrelated Guzzle-layer bugs found earlier in the same investigation thread.

**How to apply:** before adding new async work to `Chat.php`/`EngineBackend.php`, reuse the fork+non-blocking-socket-or-timer pattern already established (don't reinvent). Before adding a new `Backend` implementation, never call `Loop::stop()` from inside it. Before writing a test that touches `Loop::get()`, always await/settle every promise you create in it.


## `project-sugarcrush-guzzle-baseurl-bug`

*"sugar-crush's sglang/custom OpenAI-compatible providers 404'd because Guzzle drops a base_uri path suffix when the request URI starts with '/' — fixed in PR #1399, but the same gotcha applies to any future provider built the same way."*

<sub>originally `project_sugarcrush_guzzle_baseurl_bug.md`, type `project`</sub>

`SglangProvider`/`CustomProvider` (`sugar-crush/src/Providers/`) build a Guzzle `Client` with `base_uri` set to a config value that can carry a path (e.g. `.sugar-crush/config.dev.json`'s `dev-sglang` → `https://skynet2.interserver.net/v1`), then issue requests against `/chat/completions` (leading slash). Guzzle resolves relative request URIs against `base_uri` per RFC 3986: an absolute-path URI (`/chat/completions`) REPLACES the whole base path instead of appending, silently dropping `/v1` — every completion request 404'd at the bare host.

Fix (PR #1399): trailing-slash `base_uri` (`rtrim($baseUrl, '/') . '/'`) and use relative request paths with no leading slash (`chat/completions`, `embeddings`) in both providers' `openAiCompatible()` constructors.

Same PR also fixed a second, independent live crash in `SglangProvider::completeStream()`: it called `GuzzleHttp\Psr7\Stream::readLine()`, which does not exist on Guzzle's real PSR-7 stream (only `read()`/`eof()` do) — this hit on every real chat message send, since `Runtime::run()` always streams by default. The existing test had mocked a fictional `readLine()` onto the stream double, which is exactly what hid the bug; rewritten to stub only real `StreamInterface` methods. `CustomProvider::completeStream()` already used the correct manual read+buffer+newline-split approach — that's the pattern to copy for any new streaming provider.

**Why:** the user hit this live testing the sglang backend wired up in [[project_sugarcrush_tui_and_parallel_tools]] — reported "404" and then, after the base_uri fix, a live crash on `readLine()` on the very next message.

**How to apply:** any new OpenAI-compatible provider added to `sugar-crush/src/Providers/` must trailing-slash `base_uri` + use relative request paths, and must implement `completeStream()` via manual `read()`+buffer+`strpos("\n")`, never `readLine()`.

## `project-sugarcrush-render-overflow-bug`

*"sugar-crush Renderer must clip the frame to terminal height, not just pad it — candy-core's Renderer clamps out-of-bounds cursorTo() and collides rows once content grows past one screen. Read before touching Renderer::render()'s full-window layout code again."*

<sub>originally `project_sugarcrush_render_overflow_bug.md`, type `project`</sub>

**The real root cause of "text/cursor ends up in the status bar" (PR #1403), after [[project_sugarcrush_async_and_double_diff]]'s double-diff fix (PR #1402) turned out to be necessary but not sufficient.** `Renderer::render()`'s full-window layout code (Phase 4, PR #1397) padded short conversations up to `rows - 1` lines but never clipped tall ones — it only ever grew (`$targetRows = max(count($contentLines), $rows - 1)`). candy-core's own `Renderer::render()` (`candy-core/src/Renderer.php`) repaints only *changed* rows via an **absolute** `Ansi::cursorTo($row, 1)` — it has no concept of scrolling; it assumes the whole frame always fits within the real terminal (this is a "full-screen dashboard" renderer, not a scrolling-transcript one). Once sugar-crush's chat frame (history + input + status bar) grew taller than the actual terminal — trivially easy, e.g. one multi-line assistant reply in a normal-height terminal — every `cursorTo()` for a row past the terminal's last physical row gets **clamped there by the terminal itself** (standard VT/xterm CUP behavior). Distinct logical rows (input box, status bar, newest history lines) all collide onto that single physical bottom row, which is indistinguishable from "my typed text/cursor is showing up in the status bar" and also explains why Ctrl+P's palette (composited via `Veil` centered on the *oversized* frame string) never appeared anywhere visible on screen — its center was computed relative to a frame many screens tall, landing the overlay far outside the actual viewport.

**Fix:** clip `$contentLines` to the tail (`array_slice($contentLines, -$available)`) when it exceeds `rows - 1`, instead of only padding when it's short. Frame is now unconditionally exactly `$rows` lines. Old history scrolls off the top (lost, not scrollback-preserved — alt-screen mode has no native scrollback anyway); the input box (rendered as the tail of `$content`) and newest turns stay visible right above the status bar.

**Also fixed same PR:** 5 test files (`tests/LSP/LspClientTest.php`, `tests/Workflows/Workflow{Engine,Result}Test.php`, `tests/Context/InstructionFileLoaderTest.php`, `tests/Tui/AgentOutputPaneTest.php`) had their namespace nesting inverted — `SugarCraft\Crush\<Sub>\Tests` instead of the `autoload-dev` map's expected `SugarCraft\Crush\Tests\<Sub>` — composer silently skipped them from the autoloader with a PSR-4 warning on every install/dump-autoload. Simple namespace-declaration swap, no other file referenced the wrong namespace.

**Follow-up (PR #1404): the #1403 fix alone didn't fully land, because $rows itself could be wrong.** #1403 clipped to `TuiRenderer::getTerminalSize()['rows']` — but that's a SECOND, independent, statically-cached size detector (`(new Tty(STDOUT))->size()`, cached forever, never invalidated) separate from the size candy-core's `Program` itself detects and dispatches via `WindowSizeMsg` at startup and on every SIGWINCH resize (project invariant: "WindowSizeMsg is size truth" — see [[project_tui_render_invariants]]). `Chat` never handled `WindowSizeMsg` at all before this. If the two size sources disagree even slightly — or the terminal is resized mid-session, which the cache never re-learns — the exact row-collision bug comes right back, indistinguishable from the original symptom, which is why the user still saw it after #1403 shipped. Fix: `Chat` now stores `rows`/`cols` from `WindowSizeMsg` (`rows()`/`cols()` accessors, falling back to `TuiRenderer::getTerminalSize()` only when no `WindowSizeMsg` has arrived yet, e.g. a `Chat` built directly in a test); `Renderer::render()`/`renderAgentView()` read `$chat->rows()`/`$chat->cols()` instead of querying terminal size themselves.

**How to apply:** any future change to `Renderer::render()`'s layout math must preserve "frame is always exactly `$rows` lines, never more" — candy-core's Renderer has no scrolling and will silently corrupt the screen the instant that invariant breaks, no matter how correct the content generation logic is otherwise. Get `$rows`/`$cols` from `Chat::rows()`/`cols()` (sourced from `WindowSizeMsg`), never from a fresh, independent terminal-size query — two independent size detectors for the same terminal is itself the bug class. Before trusting a "diff renderer" bug report as fixed, check whether the frame can just be too tall for the terminal, AND whether the size used to bound it actually matches Program's own live-detected size — either mismatch produces an identical-looking symptom.

## `project_tui_render_invariants`

*"candy-core diff renderer invariants — no over-wide lines, WindowSizeMsg is size truth, sanitize DB/binary data"*

<sub>originally `project_tui_render_invariants.md`, type `project`</sub>

The candy-core frame-diff `Renderer` (candy-core/src/Renderer.php) positions each frame line at an absolute terminal row via `cursorTo($i+1,1)`. This assumes **one frame line == one physical terminal row**. Two invariants follow for any Model `view()` in this repo (candy-query, sugar-*, etc.):

1. **No rendered line may exceed the terminal width.** An over-wide line wraps, breaking the 1-line-per-row mapping and cascading into screen corruption (fragments, drift, growing garbage). Measure widths with `SugarCraft\Core\Util\Width::string()` (display cells), never `mb_strlen` (codepoints) — they diverge on CJK/combining/emoji. Truncate with `Width::truncate()`. When composing nested bordered panes, remember a candy-sprinkles `Style->border()->padding(0,1)` adds **+4** to the content width, and the outer frame's content area is `cols-2`.

2. **The framework owns terminal size.** `Program` emits `WindowSizeMsg(cols,rows)` at startup and on SIGWINCH. Models must consume it (candy-query forwards it to `Renderer::setSize()`), not independently re-detect + cache size — that desyncs from the screen the diff renderer drives and breaks resize.

3. **Sanitize untrusted/binary data before rendering.** Raw control bytes (NUL, BEL, and especially a stray ESC `0x1b`) from DB BLOB columns inject bogus escape sequences that desync the renderer. candy-query's `Renderer::cellString()` repairs invalid UTF-8 and strips C0/DEL/C1. Also: don't run a synchronous DB query per keystroke in `update()` (it blocks the loop — froze candy-query for minutes over remote MySQL).

Also fixed: `candy-core` `PosixBackend::size()` now prefers the live `TIOCGWINSZ` ioctl over `COLUMNS`/`LINES` env (env is stale under SSH/tmux → wrong/half height). See [[project_stale_vendor_false_test_failures]] before trusting local phpunit failures.

4. **Writers MUST loop over short writes.** `Program::run()` sets STDIN non-blocking via `stream_set_blocking($input,false)`. Shell-launched fds 0/1/2 are dups of ONE open file description of the controlling tty, and `O_NONBLOCK` lives on the *description* — so this also makes **STDOUT non-blocking**. A large first frame (full-screen, tens of KB) then gets a short `fwrite()` count over a partly-full PTY buffer (esp. SSH), and the dropped tail = a **non-deterministic** partial paint each launch ("different amount every time, fills in as you scroll" — small per-keystroke diffs always fit). Fix: `Renderer::emit()` + `Program::writeOutput()` loop until all bytes flush, `stream_select`-ing for writability on a 0/EAGAIN return. Diagnose any "amount painted varies per launch" TUI bug here first.

5. **The outer frame must be EXACTLY `rows × cols`.** candy-query `BorderFrame::wrap()` emits 6 structural lines (top, title, divider, divider, status, bottom) — NOT 7; an off-by-one left the frame one row short of full height. Pad content up AND truncate down to exactly `rows-6` content lines so the total is always `rows`. And `padRight`/`padCenter` must re-measure after truncating (`Width::truncate` can stop short of the requested width → a 1-cell-short line misplaces the right border `║`). A constant `rows×cols` rectangle every frame also keeps the diff renderer's line count stable.


## `project_vhs_tape_multi_directive_lines`
