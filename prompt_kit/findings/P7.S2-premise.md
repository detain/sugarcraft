## Design decisions the orchestrator must make BEFORE briefing

**A. SessionStart fire point (claim 4a).** Recommended: **inside `submit()`, guarded by `count($this->history) === 0`, prepending `Message::system($note)` to `$newTurnMessages` before `Message::user($text)` at :6084-6099** — literal match to the plan's "start of a conversation, before the first prompt", one fire point, rides the proven request path, trivially testable (fresh Chat has empty history). Rejected alternatives: `Bootstrap::chat()`/`withHooks` (immutable-model problem, async-command plumbing); `init()` (cannot mutate). If resume/new-session-mid-run coverage is demanded, add a second fire in `handlePaletteNewSession` (:11228) — but the done-when doesn't require it; ship first-turn-startup only and document the gap.

**B. Message mechanism: role:system vs `<system-reminder>` (claim 5).** role:system is **executable today** on all five wire providers (OpenAI/Anthropic-via-CustomProvider inline; Bedrock/Vertex order-preserving hoist; repo precedent = `contextReminderMessage` Chat.php:12044 sent every due turn). Keep the plan's PREFER. One caveat to fold into the brief: SglangProvider:1518 warns mid-conversation system content may be template-ignored — accept, it's a non-primary driver.

**C. Context payload transport (additional facts).** Prompt text rides `HookContext::toolInput` (decision to make: `toolName = 'UserPromptSubmit'` sentinel vs empty — upstream sends `prompt` in JSON but candy-code's script protocol is env-only). For SessionStart: pass `model`/`provider` if cheaply available, else empty as `gateToolCall` already does. Decide NOW whether to extend `HookContext` with `prompt`/`source` fields (cleaner env names, ripple: 3 `with*` + all ctor sites + tests) or document `toolInput`-as-prompt smuggling (zero ripple). Either is defensible; smuggling keeps P7.S2 inside its 5-file list — extending HookContext does NOT (adds src/Hooks/HookContext.php + ScriptHook.php to the blast radius; ScriptHook env names also need `CRUSH_PROMPT`).

**D. Dispatch class + test placement.** Methods go on **HookManager** as `sessionStart()`/`userPromptSubmit()` 2-line `executeHooks` clones (claim 1) — do not build on HookDispatcher. Consumers: null-safe `$this->hooks?->...` in `Chat::submit()` mirroring `applyPostToolUse`'s empty-note-no-op contract (:3676-3686). The plan's file list already fits: `src/Chat.php` gains the two call sites; `HookDispatcher.php` arguably shouldn't be touched at all (plan lists it — orchestrator may want to downgrade it to "docs note about remaining dormant events" or drop it from scope). Test: new file under `tests/Chat/` (e.g. `SessionStartHookWireTest`) using the `ReminderWireRecorder` pattern (assert `Role::System` + text in `lastHistory()`, ContextReminderDedupTest.php:201-205) — and if the done-when's literal "provider receives" wording must hold, the two-step `EngineBackend(recordingProvider)->complete($next->history)` from RulesCommandTest:484-498; **never** a Chat-driven `completeAsync` + provider double in-parent (pcntl fork trap, claim 6).

**E. Semantics edge to pin in the brief:** `HookEvent::discardsOnBlock()` says UserPromptSubmit blocks discard the *prompt* (:84) and `stderrToUserOnly()` covers SessionStart (:95-96) — P7.S2 should honor or explicitly defer these enum-declared semantics; the plan text is silent, and `applyPreHooks`' deny path shows what honoring looks like.
