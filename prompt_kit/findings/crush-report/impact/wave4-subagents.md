## Per-step notes

**4.1.** Today the engine path ignores the preset's `model`, `effort` and `permissionMode`. The TaskTool doc :99-109 records this as policy. `Agent::fromPreset` already carries all three (`inherit`/'' resolves to the launch model). Three risks:
- **Effort default.** `AgentPreset::$effort` defaults to `Effort::Medium`, and `parseEffort` falls back to Medium on an unknown spelling. If effort is honoured as-is, every sub-agent sends `medium`, which overrides SGLang's per-model default (Qwen3-Next = `xhigh`, :334). Make the field nullable (or add a sentinel) and refuse an unknown spelling. `QWEN3_NEXT_TEMPLATE_EFFORTS` = low|medium|xhigh, so a preset `effort: high`/`max` must fail loudly on that model.
- **Model aliases.** Claude-dialect aliases (`sonnet`, `opus`) mean nothing on SGLang. Resolve them in this order: per-call `model` arg, then preset (non-inherit), then `subagentModel`, then session. Refuse loudly when the provider cannot serve the result (single-served-model providers: compare with `servedModel()`).
- **Permission mode.** The `createSubAgent` mid-session seal must become narrow-only per sub-agent. Never widen: the preset gate is a second gate (both must pass).

Split: **4.1-1** (model + effort + `withModel`, shared with N-P3b) → **4.1-2** (mode).

**4.2.** Confirmed hole, not just a dormant nicety. The engine path narrows by tool **name** only (`grantedToolsFor` → `resolveGrantedTools`, which drops argument halves by design). The per-call half (`refuseCallOutsideGrant`) is reachable only from `executeSubAgent()`, which has no `src/` caller. So `Task(agent: reviewer)`, declared `['Read','Grep','Bash(git *)']` (`AgentDefinition.php:89`), runs **any** Bash command the session gate allows. Argument-scoped `disallowedTools` such as `Bash(git push*)` are not enforced on the live path either.

Fix: a `SubAgentGrantHook` registered in `resolveHookManager` before `PermissionGateHook`. It is registered even under `withoutHooks()`, as the gate is, so it is not an opt-out. Reuse the existing matcher (Deny = union, Allow = intersection, root-aware). Correct the comment at `AgentDefinition.php:85`.

**4.3.**
- **4.3-1:** `/bg` output is buffered by the daemon, and `restoreOutput` already exists. Only `pumpBackgroundSessions` drops it, emitting a status-only `Message::notice`. The announce row must be agent-visible (user role) so the model sees the result. Auto-dispatch when idle; queue when busy until 1.C-3 provides steer.
- **4.3-2:** The tool runs inside the turn child, so the parent must learn about the spawned daemon. Proposal: bind Chat's supervisor into TaskTool. The fork inherits the IPC dir. The child spawns the daemon and emits an `OP_BACKGROUNDED` frame (P-B1 owns the DTO), and the parent calls `adoptSession()`. The daemon today runs `backend->complete([user(task)])` with the full tool set, so it must run the preset through `AgentManager` + TaskTool to keep the grant (4.2) and resume. A daemon has no UI: Ask = deny, stated in the result.
- **4.3-3:** `reconnect()` (:1298) only iterates `$this->sessions`, and the IPC dir is per-process random (:682). After a restart it therefore adopts **nothing**, even with a caller. It needs a stable per-uid dir plus a disk index before either the TUI or O-4b can call it.

**X-30.** Confirmed. `handleForkCommand` forks the session rows and passes the id only as a tag (`['fork','session:<id>']`). `BackgroundSessionRunner::executeTask` calls `complete([Message::user($this->task)])` and never sees it. Pass the id in the daemon config (never the bytes: argv is world-readable), load it with `Bootstrap::sessionStore(false)->loadTranscript()`, and write the reply back so the fork is a real resumable session. Keep it separate from 4.3 and land it first: 4.3-2's `resume` reuses the same runner history seam.

**4.4.** Accept the sessions-agentview split:
- P-D1 owns `AgentInbox`/`AgentMessage`/`MessageMode`/HMAC and the `TurnInbox` drain.
- 4.4 owns only the model-facing tools: `SendMessage{to,text,mode}`, `Subagents{list|wait|cancel}`, `InterruptAgent`, and the child→parent reply. They call `AgentInbox::send(from:'parent'|'agent:<id>')`, framed as untrusted.
- "cancel" reuses P-D3's soft-cancel. Cold resume of a stored agent needs 4.7-1 (today only failed or step-capped runs are saved).
- Three new BuiltIn files take the directory from 12 to 15, which is outside `DocFigureProseDriftTest`'s word map (`ten`..`thirteen`). Consider one `Subagents` tool with an `action` enum to limit roster growth.

**4.5.** Disjoint from the P-* work. Same lifecycle as `SiblingSpendLedger`: one board per parallel batch, created in `executeConcurrently` and given to members. Notices ride `HookResult::$additionalContext` on PostToolUse, which is already model-visible, so no Runtime result-path edit is needed. HOLD/VETO are advisory text, not locks.

**4.6.** Accept the sessions-agentview proposal: 4.6 = `TeamManager` + team tools only, and the four inert shell commands go to P-D3. `TaskList` has no revision column and `addDependency` accepts cycles, so harden them first (4.6-1). Teammates need background execution (4.3-2) and an inbox (P-D1), so 4.6-2 lands last in this batch.

**4.7.**
- **4.7-1:** Today a clean report forgets the suspension (:723-725). Save every run instead, and return the resume id with the report. Partial output on failure today is only the activity trail on the row, so add a transcript tail.
- **4.7-2:** Nothing in `runTurn` looks at the context window. The nudge is per step and sub-agent-only.
- **4.7-3:** Depth is 1 by construction (filter :493-496) and the parallel batch has **no** concurrency cap. Caps (depth 3, 8 concurrent) need N-P4f's settings rows. 4.7-3 and RELAY both edit `turnTools`/`executeConcurrently`, so run them in sequence.

**4.9.** `WorktreeManager`, `withWorktreeRoot()` and `BashEscapeDenyHook` exist and are tested, but nothing in `src/` constructs `WorktreeManager`. Risks:
- `withWorktreeRoot` re-jails the tools but leaves `root`, so the env block and permission-rule root still name the main checkout.
- Worktree creation runs `exec(git worktree add)` from inside the turn child, which is fine.
- Cleanup policy: keep a dirty tree and name it in the result, so work is never silently deleted.
- `/bg` uses the same manager via `workingDirectory`.

**4.10.** 15e reclassified "only the first task of a stage runs" as intentional and unreachable from YAML (`parseYamlStage` builds one task per regular stage). It becomes reachable only if 4.10's plan schema accepts `tasks:` lists, so do 4.10-1 (sequential multi-task stages) first, then the tool. Risks:
- `bindEngineBackend()` is a void setter on the shared pool's executor. The tool must bind per call inside the turn child and never in the parent.
- Stage agents fork grandchildren whose activity is invisible until RELAY lands.
