## Per-step notes

**2.1.** Put the check at the top of each step in `runTurn`, not in Chat. Sub-agents get it for free: `TaskTool::runOnEngine` :611 and `EngineExecutor` :228 both go through `completeTranscript` → `runTurn`. The anchor is the last step's `AssistantMessage::usage()->promptTokens()`, plus a `TokenEstimate` of the rows added since. Leave Chat's meter alone here; counting system + tools in the submit estimate (`rawTokenProxy` :17573) belongs to O-2c/5.6, so 2.1 does not touch the O-2c region. On its own, 2.1 only detects pressure and emits an event; the actions arrive with 2.2-1 and 2.4-1.

**2.2.** `removeToolResults` keeps only rows that are not (`role=system` with `tool_results`). `Message::toWire` :731 never emits `tool_results`, and Chat stores tool output as `Message::assistant(...)->withToolResults()` (`Chat::toolResultMessage` :4639), so the filter never removes anything. Within a turn, `$app->messages` holds real `ToolResultMessage`s, so 2.2-1 works today. Across turns, `toTypedMessages` replays tool output as assistant prose, so there is nothing typed to replace until 1.B-2. That is why the step splits in two. **Key `PruneEntry` by tool-call id** (unique after 0.2 and already persisted in `toolResults[].id`), not by row ref. This removes 2.2-1's dependency on 1.B-1. Row refs and the ref→id map arrive with 1.B-1 / 3.B.

**2.3.** Adds only new files, so it can run in parallel with anything after 2.2-1. Path keys come from tool-call arguments, which within a turn exist only on typed `AssistantMessage::toolCalls()`. Cross-turn dedup needs 1.B-2.

**2.4.** 2.4-1 (engine) gives in-turn relief with no Chat change. Its block lives only in the child's `$app` until 2.2-2 carries it back over the ledger frame. Until then the next turn re-sends the full history and Chat's 85% tier still fires, which is correct but wasteful. 2.4-2 routes Chat's compaction through the main backend. Risk: EngineBackend forks per call, so the summary request must not count against the 120 s watchdog any differently from a turn.

**2.5 / 2.12** sit in the same Chat methods as 1.B-3. Land 1.B-3 first, then run 2.12 and 2.5 one after the other (2.12 is smaller). For 2.12, use the same `trigger` value as Claude Code: `manual` for `/compact`, `auto` for the 85% tier and step-level compaction.

**2.6.** Do not read files in `Chat::update()` (TUI render invariant). Read them in the child when the turn context is rendered. "Files read/modified" comes from `FilesTouched` (2.5). The todo/plan re-injection waits for 3.C.

**2.7.** Three independent sub-steps. Classification (`ContextOverflow`) touches only providers and can run in parallel from day one. The retry needs 2.2-1/2.4-1 to have something to shrink. Keep the prefill edits out of `SglangProvider::formatMessages` :2316-2360, which 1.A owns, and put them in the request-params builder instead.

**2.8.** Spilling inside the trait sees the full captured text. A central spill in `Runtime::settle` sees only text that is already clipped, so it is needed only for tools that don't use the trait. Biggest risk: the `PathJail` allow-list, since a spill dir outside the root must be readable by `Read`/`Grep` but nothing else. It collides with N-P4c (same constants), 0.5 (MCP caps) and 0.12 (Read paging); give one owner per wave.

**2.10.** Background summarisation means a second `pendingCompactionId`-style latch. Generation and `/clear` invalidation must follow the `pendingCompactionId` rules (:2025-2044).

**2.11.** The roadmap (IV.5) already orders it `0.6 → 5.1 → 5.2/5.3 → 2.11`. Treat it as a Wave-5 item placed here.
