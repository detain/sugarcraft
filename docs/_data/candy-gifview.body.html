candy-gifview is a terminal GIF viewer. Point it at a .gif and it decodes the file with ext-gd, sizes the frame grid to your terminal, and plays the animation in the alternate screen as 24-bit background blocks or as an ASCII luminance ramp. The decode, render and playback layer lives in sugar-animation. This package is the command-line front end over it, and GIF is the only input format it reads.

Install

composer require sugarcraft/candy-gifview   # binary lands in vendor/bin/candy-gifview

Requires PHP 8.3 or newer and ext-gd, which is declared in composer.json, so the platform refuses an install without it. The CLI also checks for ext-gd before it touches the file, and exits non-zero with a clear message if it is missing.

A rolling phar is published on GitHub Releases as candy-gifview.phar. The channel is frozen at the 2026-11-04 build, commit f1c90bb34, because rolling rebuilds are blocked fleet-wide. Until the release page shows an artifact newer than that date, prefer the Composer install. To check a download, compare the .sha256 sidecar and the .phar.commit sidecar. No minisign key is anchored for this app yet, so these two files show what you hold rather than who built it.

sha256sum -c candy-gifview.phar.sha256   # integrity
grep -m1 . candy-gifview.phar.commit     # which build you actually hold

Quickstart

candy-gifview my-animation.gif            # solid 24-bit blocks (the default preset)
candy-gifview my-animation.gif density    # ASCII luminance ramp
candy-gifview --fps=12 --paused clip.gif # a uniform 12 fps, starting on the first frame

With a project-local install, run ./vendor/bin/candy-gifview instead. The synopsis is candy-gifview [options] <gif> [solid|density]. Flags may appear before or after the positional arguments.

Concepts

The viewer has three stages. Intake reads the file and decodes it into frames, sized to a grid of terminal cells. Playback schedules those frames on the clock the GIF's own delays define, or on a rate you choose. The renderer paints each frame with SGR escapes into the alternate screen, and quitting restores the terminal's prior contents.

Both presets emit 24-bit truecolor SGR. solid paints the cell background (48;2) with a space glyph. density paints the foreground (38;2) on a luminance ramp of characters. The viewer paints with escape sequences rather than a terminal graphics protocol such as kitty, sixel or iTerm2, so it works anywhere 24-bit color does. Inline graphics are a different route, offered by sugar-image.

Sizing the viewport

The viewer sizes the frame grid through sugar-core's terminal façade. An explicit COLUMNS and LINES pair, both positive integers, wins first. Otherwise stdout is probed. Off a terminal, such as piped output or CI, the grid falls back to a deterministic 60 by 24 cells. A probe failure therefore cannot crash the run, and the worst answer is the fallback grid.

Frames are decoded once, at the launch size

Growing the window reveals no extra detail, because frames were decoded at the launch size. Shrinking the window re-clamps the grid and crops the frame. Only a restart re-queries the terminal, and a --watch reload also re-decodes at the frozen launch budget.

Tasks

Play at a fixed rate or a multiple of the GIF's rate

candy-gifview --fps=10 clip.gif          # a uniform 10 frames per second
candy-gifview --speed=2 clip.gif        # twice the GIF's average rate
candy-gifview --speed=24fps clip.gif    # an absolute 24 frames per second
candy-gifview --fps=10 --speed=2 clip.gif   # plays at 20 fps: the multiplier composes onto the rate

The rate arithmetic runs on three slots. A rate slot is written by --fps=N and by --speed=Nfps, so the last of those wins. A multiplier from --speed=N composes onto whatever the rate slot holds, so the flag order does not matter. --speed=max is a latch: once seen, it overrides every other rate flag and a later flag cannot clear it.

Stop by itself, for scripts and CI

candy-gifview --duration=5 clip.gif < /dev/null     # stop after five seconds of playback
timeout 5 candy-gifview loop.gif < /dev/null      # or let timeout(1) end it; exit 124 when the timer fires

An animation with no finite loop count repeats forever. With stdin at end of file, a run with no --duration never ends on its own. --duration counts playback time, not wall time, so paused time does not count. It needs at least two frames, and a single-frame file with --duration is refused.

Reload the file when it changes

candy-gifview --watch frames.gif

--watch polls the file every 10 ms on the event loop and reloads it when it changes. A reload runs its decode synchronously inside the poll tick, so a large replacement file can stall one tick. A reload that trips a cap keeps the stale frames rather than blanking the screen.

Start paused and step through frames

candy-gifview --paused clip.gif   # opens on the first frame; Space resumes, arrows step

Playback can start paused, and it is fully steppable by key. ← and → step one frame and wrap at the ends. This is also the way to meet the reduced-motion preference, since the viewer does not read the environment for it.

Answer in another language

candy-gifview --lang=de clip.gif   # German messages, whatever LC_* says

The --lang flag is resolved before the first message prints, so it works on hosts where no LC_* variable exists, such as native Windows cmd. An unknown code is refused in plain English, and the refusal names the locales that are available.

Classes from sugar-animation

The viewer's playback and decoding are provided by sugar-animation. Decoder holds the limits MAX_FRAMES (256 frames), MAX_CELLS (100,000 output cells) and MAX_TOTAL_PIXELS (2,000,000 source pixels). Player holds MAX_FPS, and it is the player that Cli::main() wires and passes to the $play seam. See the sugar-animation page for those classes.

Options

--lang=CODEAnswer in one of the 16 bundled locales, regardless of the environment.

A standalone -- ends option parsing. Every token after it is a path, so a GIF named -foo.gif can be played as -- -foo.gif. A bare - is not read as stdin. It is an ordinary path, and it is refused as could not play '-'.

The loop count in the file

A loop count of N in the GIF means N extra repeats after the first play, so N+1 passes in total. A count of 0, or a file with no loop extension, plays forever. That forever default deliberately differs from the single-play answer of libnsgif.

Theming

The two presets are the only styling. solid is the default and suits pictures, and density suits legibility, since its character ramp survives color-blind viewing and poor-color terminals. Switch with the preset argument at launch, or press d during playback.

candy-gifview clip.gif solid
candy-gifview clip.gif density

There is no 256-color fallback and no NO_COLOR or monochrome mode. On a terminal without truecolor the blocks degrade to default or nearby colors. On TERM=dumb or other capability-poor terminals, expect raw escape sequences rather than a usable frame. Transparent GIF pixels are composited against the terminal's own background.

Examples

The examples/ directory holds three PHP programs. They load the Composer autoloader, so run them from a checkout after composer install.

  • examples/view.php builds a small synthetic animated GIF in a temporary file and plays it through Cli::main(), the same entry point the binary uses. The file is removed on exit. Any extra arguments are passed to the CLI, so php examples/view.php --duration=1 < /dev/null finishes by itself. This is the program behind the demo GIF below.
  • examples/refusals.php runs Cli::main() on four argument vectors, --help, --version, a bad preset and a missing file, with memory streams and a stub player. It prints each exit code and the first line of output, so you can see the exit-code contract without a terminal.
  • examples/version-stamp.php shows how Version::normalizeStamp() and isStampable() treat a release tag, a bare release, a development build and an unrecognized string.
php examples/refusals.php < /dev/null
php examples/version-stamp.php < /dev/null
php examples/view.php --duration=1 < /dev/null

Testing

The suite runs under PHPUnit 10. Run it once from the package root, with stdin redirected:

cd candy-gifview && composer install && vendor/bin/phpunit < /dev/null

The tests cover the entry point, the watch loop and the binary. CliTest and CliLoopWatchTest drive Cli::main() through its seams. BinBootTest and BinSizeQueryPolarityTest cover the bin/candy-gifview shim. WatchRealHostTest exercises the watcher against the real filesystem. VersionTest covers the stamp grammar, and LocaleParityTest checks that every lang/ catalog carries the same keys. PharBuildScriptTest covers the phar build.

Troubleshooting

The process never exits

The GIF has no loop count, so it repeats forever, and with stdin at end of file nothing quits it. Pass --duration=N, or run the viewer under timeout(1). Under timeout, exit 124 means the timer stopped the run.

Exit 1 when ext-gd is missing, or a file fails to decode

The CLI needs ext-gd to decode GIFs. Install it, for example with apt install php-gd on Debian-based systems, and check it with php -m. A file that fails to decode also exits 1. Either way the message is written to stderr.

Output is raw escape sequences

The terminal lacks truecolor, or TERM is dumb. The blocks degrade on a limited palette, and density stays legible there. On TERM=dumb there is no usable frame, and the viewer cannot help with that.

The viewer is the wrong size

The grid is sized once at launch. A window that is grown after launch keeps the old frame detail, so restart the viewer. Off a terminal, the grid is the 60 by 24 fallback. Set COLUMNS and LINES to size it explicitly.

A large file is refused, or the first frames are missing

A file over 64 MiB is refused. The engine decodes at most 256 frames, and a longer file is cut to its first 256 frames. A notice on stderr says so. A file with exactly 256 frames gets the same notice, because a full window and a truncated stream look the same to the engine.

A --watch reload leaves the old frames on screen

A reload is refused when it trips a cap, and then the stale frames stay on screen. A large replacement file can also delay one tick, because its decode runs synchronously. Check the file's size against the caps listed under Limits.

Intake is bounded by the read itself. At most the cap plus one byte is pulled, and the length actually seen decides, so a file that grows during the read cannot slip past the cap. FIFOs and devices are refused by an is_file() check before the open.

Exit codes

CodeMeaning
0--help or --version printed, or playback ended normally
1A flag or argument refusal, the ext-gd refusal, or a decode failure. The message is on stderr.
128+NThe loop was stopped by signal N. For example, 143 is SIGTERM.

Accessibility

  • The density preset encodes brightness as character density, not only as color, so it reads on colorblind viewing and poor-color terminals.
  • Playback can start paused with --paused, and it can be stepped one frame at a time with the arrow keys. Motion is never required to see the content.
  • The frame rate is capped at the player's own scheduler floors. --speed=max is opt-in and is never the default.
  • Reduced motion is not detected automatically. The viewer does not read REDUCE_MOTION or PREFERS_REDUCED_MOTION, so motion-averse users should pass --paused. This is a known gap against the fleet convention.
  • CLI messages are localized into 16 locales. The status line during playback is English only.

Architecture

Intake, then playback

Cli::main() parses flags, checks ext-gd, reads the file under its caps and decodes it into frames sized to the grid. It then wires a Player from sugar-animation and runs the program loop on it. The $play seam replaces that last step for tests and examples.

Language is fixed before output

--lang is scanned before anything prints, so the locale is set before the first message. The unknown-code refusal is an English literal, because a localized refusal would need a locale the user has not yet chosen.

Changelog and versioning

The version is Version::CURRENT, 0.1.0, in a checkout. Inside a phar, the build stamp replaces it. A release stamp is a bare version such as 1.4.2, and a development stamp is dev- followed by a commit hash or dev-build. A development stamp prints verbatim, so a development phar never looks like a stable release.
