Terminal AI coding agent, inspired by charmbracelet/crush. It talks to eleven provider type keys over nine engines, runs thirty-eight built-in tools on every launch behind hooks and a six-mode permission gate, keeps per-turn workspace checkpoints with undo and rewind, prunes and compacts its own context, runs sub-agents you can watch and message, and reads skills, memory, MCP servers, workflows and SQLite-backed sessions. It also serves a WebSocket API with a browser UI and an Agent Client Protocol agent for editors, all on the sugar-core render loop with Markdown replies. With no configuration it runs offline on the built-in echo provider.

Install

composer require sugarcraft/candy-code

Requires PHP ^8.3. The package declares its sugarcraft/* siblings with the @dev constraint (composer.json), so a host project must allow dev-stability packages: set "minimum-stability": "dev" with "prefer-stable": true in that host, or run it from a checkout of the monorepo. The package's own composer.json declares both keys (lines 111-112), but Composer reads stability settings from the root project only, so that declaration does not reach a host. A container build is described in docs/DOCKER.md.

Winget and Scoop are not documented as install channels, on purpose. Their manifests in candy-code/packaging/winget and candy-code/packaging/scoop are templates with {{VERSION}} and hash placeholders, and no workflow in the repository renders or publishes them, so a Winget or Scoop command here would name an install that does not exist. The install script and the Homebrew formula described in the README remain the standalone installs. Running candy-code in CI, with the composite action and the GitLab example, is covered in docs/CI.md.

Quickstart

Step 1. Run it with nothing configured. The binary falls back to the offline echo provider, so no network and no key are needed. This is the output of a real run, captured with no provider environment and an empty HOME:

$ candy-code -p "explain the Width helper"
You said:

> explain the Width helper

The line candy-code: no provider configured (…); answering from the offline echo provider. goes to stderr, which is why it is not in the output above. -p is the one-shot mode: it never attaches to the terminal and never opens the alternate screen. Run candy-code with no arguments for the full TUI.

Step 2. Point it at a real model. The provider is chosen by CANDY_CODE_PROVIDER, and the provider's own environment variables supply the key (see the providers table below):

export CANDY_CODE_PROVIDER=openai
export OPENAI_API_KEY=sk-...
export CANDY_CODE_MODEL=gpt-4o     # optional; the provider default otherwise
candy-code

A provider run needs a key and network access, so its output is not captured on this page. The offline run above is the reference output.

Step 3. One-shot with JSON output, for scripts. The unattended -p mode starts in the default permission mode and refuses any tool call that would ask, so pass --permission-mode when a script needs tools. This is the captured output (the session_id differs on every run):

$ candy-code -p "audit this" --output-format json
{"schema":1,"result":"You said:\n\n> audit this","refusals":[],"session_id":"3b8c2910e15dae8b"}

$ candy-code -p "audit this" --output-format json | jq -r .result
You said:

> audit this

For a provider-free backend, CANDY_CODE_BACKEND_CMD names a script that reads the JSON history on stdin and writes the reply to stdout; CANDY_CODE_BACKEND_CMD_STREAM is the token-stream variant. Every variable is listed in docs/ENVIRONMENT.md. The step-by-step first run is in docs/TUTORIAL.md.

What it is

Eleven type keys, nine enginesOne ProviderInterface with capability introspection (supportsStreaming(), supportsVision(), contextWindow(), costPer1kTokens()), streaming, function calling and embeddings. OpenAI and Azure share one engine; Anthropic, Claude Code CLI, Codex, SGLang, Bedrock, Vertex, Gemini, and custom (with OpenRouter as a preset) make up the rest. The Claude Code and Codex routes run each turn inside the vendor's own signed-in CLI.
Bounded agent loopEngineBackend::complete() calls the provider, runs the returned tool calls through the hook gate, feeds results back, and repeats until the model answers without calling a tool or maxSteps is reached.
Thirty-eight built-in tools on every launchShell, file read, edit and write, ApplyPatch (multi-file patches, all or nothing), search, web fetch and search, skills, language server queries (Lsp), memory, repo map, todo, context pruning and compression, workflows, team board, user questions, plan exit, schedules, sub-agent messaging, media generation, canvas pages, scripts, and background and interactive shells. Path tools are jailed to the project root, plus any read-only roots in the user-tier references setting, and an edit is refused on a file that changed since it was read. Six more tools join only when their condition holds; the full list is in the tools section. Implement Tools\Tool for your own.
Hooks that can say noPre- and post-tool-use guards return allow, deny, modify or ask. Built-ins are ProtectFilesHook, ConfirmRemoveHook and AuditHook (registered by HookManager::registerBuiltIns()), plus BashEscapeDenyHook when a worktree root is set, and PermissionGateHook last, which adapts the six-mode PermissionGate onto the same chain. Hooks load from YAML, and an external ScriptHook chooses its outcome by exit code.
Progressive skillsFrontmatter SKILL.md files inject prompt context. The system prompt carries only each skill's name and description; the model loads a full body through the Skill tool. Ten built-ins ship with the app, and you can add more under ~/.candy-code/skills and <project>/.candy-code/skills, or import them from Claude Code and opencode.
Sub-agents, teams & worktreesThe Task tool delegates to agent presets, each with its own model, tools, skills and permission mode. Runs can go in parallel, nest, run in the background, or run in a git worktree of their own, and each one can be resumed. Each run gets a live line, an agents strip and an Agent View with its own transcript, where you can message, pause, cancel, or send it to the background with Ctrl+X b. SendMessage, Subagents and InterruptAgent steer sub-agents, a parallel batch shares a board, and teammates claim tasks from a shared SQLite board through the Team tool.
WorkflowsWorkflowEngine runs multi-stage agent pipelines (sequential, fan-out parallel, chained, and task-then-verifier) from a PHP DSL or YAML. A run can be paused at a stage boundary and resumed, each task can name its own agent preset, and hard token and cost budgets pause a run when they are reached.
MCP (Model Context Protocol) client & hostA multi-server client over stdio and HTTP reads .mcp.json, with ${VAR} interpolation. A project's servers start only after you trust them. The stdio host, candy-code mcp serve, exposes a fixed read-only tool roster (Read, Glob, Grep, Ls, RepoMap) to the client that spawns it. Per-preset mcpServers allowlists are enforced.
SQLite sessionsSessions, messages and tool calls persist in a WAL-mode SQLite database (~/.candy-code/session.db), with foreign-key cascades and fork, rename and resume. Opt-in retention (sessionRetentionDays) removes sessions idle for that long that have no name you gave them, skipping pinned and sub-agent sessions. A title the model generated does not count as a name, so those sessions are removed too. The database is not encrypted.
Context engineCompaction tiers with absolute token caps, summaries requested ahead of need, in-turn pruning of stale tool output, the agent's own Prune, Compress and Recall tools, re-injection after a compaction, and recovery from context overflows, cut-off replies and dropped streams.
Permissions & checkpointsSix permission modes, with rules that match a tool name and an optional argument glob. The TUI asks by default. Alt+M toggles plan mode, and the model leaves plan mode with PlanExit, which puts its plan to you for approval. Shell lines proven read-only, such as simple sed scripts that only read or for and while read loops over read-only bodies, run unasked when permissions.autoAllowReadOnly is on. A per-turn workspace checkpoint sits behind /undo, /redo, /rewind and /diff. An optional sandbox confines Bash: Seatbelt on macOS and Bubblewrap elsewhere, and it is off by default. See permissions and safety.
MemoryNotes are indexed into the prompt. A Memory tool saves, edits, deletes and recalls them with BM25 ranking, and the agent consolidates memory at the end of a turn, with a periodic review pass. A git history of the memory directory lets you restore an earlier state.
Server mode & web UIcandy-code serve runs sessions headless behind an authenticated WebSocket that speaks candy-code.v1. The CandyCodeWeb browser UI and candy-code attach drive those sessions. Remote access is gated by --allowed-host and --allowed-ips, and --allow-dir-browse (confined to --browse-root) lets a client pick a project directory for a new session. candy-code acp serves editors over the Agent Client Protocol on stdio.
Prompts from anywhere@file, @diff and @https://… attachments, $skill mentions for one turn, !command shell lines, opt-in AI! comments saved in your editor, /handoff into a fresh session seeded with a state summary, and /newrule to draft a project rule from the conversation.
Model–Update–View render loopA sugar-core Model and Program tree with buffer-diffed output: Markdown-rendered replies through SugarMarkdown, a live tool-call lifecycle, unified diffs for Edit results, inline images through sugar-image, mouse zones and text selection through sugar-mouse, and a command palette with fuzzy filtering.

How the features above are wired together is in docs/ARCHITECTURE.md. Screen-reader mode, audible cues, reduced motion and contrast are in docs/ACCESSIBILITY.md.

Providers and models

Permissions and safety

Every tool call passes a PreToolUse hook chain, whose last entry is the PermissionGate. The gate decides in three steps: a circuit breaker that denies rm -rf / and rm -rf ~ in every mode, then your rules (first match wins), then the active mode. Set the mode with --permission-mode, CANDY_CODE_PERMISSION_MODE, or permissionMode in config, and switch it in the TUI with /permissions mode. Alt+M toggles plan mode only.

ModeRuns without askingAsks, or is refused
defaultread tools such as Read, Glob and Grep, and read-only shell lines (ls, git log, grep and similar)asks for writes, other shell commands and network calls; -p refuses them
accept-editsin-project Edit and Write, mkdir, touch and rmdir on paths below the working directory, and read-only shell linesevery other shell command asks, rm, mv and cp included, as does WebFetch
planread-only Bash, and Markdown plans in .candy-code/plans/refuses everything else, and asks for WebFetch and WebSearch; the model leaves with PlanExit
autocalls the SafetyClassifier passesa security finding asks; other flagged calls are refused, or reviewed by the title model with autoReview
dont-askread-only tools, such as Read and Greprefuses everything else, WebFetch included, without prompting
bypass-permissionseverything, except the circuit breaker and your explicit deny rulesnothing

Two notes. The circuit breaker and deny rules hold in every mode, bypass-permissions included. The Bash sandbox is off by default (bashSandbox). The security model is summarized in the security section, and the full gate is in docs/PERMISSIONS.md.

Sessions, checkpoints, undo and rewind

  • Sessions. Each conversation is a session in ~/.candy-code/session.db. /sessions lists and searches them, /rename names one, /fork and /branch split a conversation, /handoff starts a fresh session from a state summary, and /session-pin keeps one at the top of the list.
  • Checkpoints. A checkpoint is taken for each turn that edits files. /diff shows what changed since a checkpoint.
  • Undo and rewind. /undo takes back the last turn, or reverts the last auto-commit. /rewind [n] [--chat|--files|--both] restores an earlier checkpoint for the conversation, the files, or both. /redo steps forward again over what was taken back.
  • Cost and pruning. /usage folds the durable spend ledger by day, model and source, /budget caps a session's spend, and /pruning sets how the session prunes its context. The context engine behind pruning and compaction is in docs/CONTEXT.md.

The FAQ answers the common versions of these questions: how do I undo what the agent changed, how do I keep a session from being pruned, and how do I cap the cost.

Hooks, skills, MCP and sub-agents

  • Hooks. Sixteen hook events, starting with PreToolUse. A hook returns allow, deny, modify or ask, and /hooks lists the chain and its log. Full reference: docs/HOOKS.md.
  • Skills. A skill is a folder with a SKILL.md file. Ten are built in. /skills lists and toggles them, and the Skill tool loads one by name. Full reference: docs/SKILLS.md.
  • MCP. Servers listed in .mcp.json are started after you trust the project, and /mcp lists, adds, logs in to and removes them. candy-code mcp serve runs the stdio host. Full reference: docs/MCP.md.

Server, web UI and editors

  • candy-code serve runs sessions headless behind an authenticated WebSocket. It binds 127.0.0.1 by default; any other address needs --allow-remote. Pin the clients with --allowed-host and --allowed-ips.
  • candy-code attach connects a terminal to a running server, and the CandyCodeWeb page drives the same sessions from a browser.
  • candy-code acp runs the Agent Client Protocol on stdio for editors. docs/ACP.md has the setup for Zed. JetBrains IDEs and Neovim take the same command and argument in their own ACP agent settings, as the guide describes.

Maintenance: gc, usage and doctor

candy-code gc reports and reclaims disk used by the session store. The verbs run from a read-only look to a destructive purge, and the order below is the order to use them in. Only gc purge and gc vacuum write. gc vacuum writes only with --force; gc purge asks you to confirm at the terminal unless you pass --force, and in JSON mode it needs --dry-run or --force.

The session store is created on the first run. On a machine that has never started candy-code, the commands below stop with cannot open the session store, so start candy-code once first (even candy-code -p "hello").

candy-code gc status                         # where the bytes are (read-only)
candy-code gc sessions --sort size --limit 20 # one row per session, real bytes (read-only)
candy-code gc analyze --top 10                # ranking, growth and orphan counts (read-only)
candy-code gc purge --older-than 90d --dry-run   # plan the purge; writes nothing
candy-code gc purge --older-than 90d --force     # the same plan, applied

Always run --dry-run first and read the plan. gc purge needs at least one filter, strip or clean flag, and it never prunes a session that --keep-latest protects. Each flag is documented in docs/GC.md.

  • candy-code usage prints the durable spend ledger, the CLI form of the /usage command. See docs/USAGE.md.
  • candy-code doctor runs the install checks and reports each row, including the sandbox row that says whether the Bash jail is enabled. /doctor runs the same checks inside a session.
  • Traces of each agent turn can go to an OpenTelemetry collector. What is sent, what never leaves the machine and what happens when the collector is down are in docs/OBSERVABILITY.md.

Security model

  • Model output is untrusted. Tool calls, edits and shell commands go through the permission gate; the circuit breaker, your rules and the mode decide each one.
  • Project files are ignored until trusted. A project's settings, hooks and .mcp.json are read only after you trust the project, and a changed MCP server definition is refused until you approve it again.
  • The server listens on loopback. candy-code serve binds 127.0.0.1 by default, and every client must authenticate. Put TLS in front of it before you expose it.
  • Secrets are plain text on disk. Provider keys saved by candy-code login sit in ~/.candy-code/config.json unless you pass --keychain. The session database is not encrypted. The storage options for login are in docs/CREDENTIALS.md.
  • The Bash sandbox is opt-in. With bashSandbox off, a Bash call runs with your privileges. When it is on, Seatbelt runs on macOS and Bubblewrap on other systems.

The threat model, trust boundaries, supported versions and how to report a vulnerability are in docs/SECURITY.md.
