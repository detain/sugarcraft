# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern:sugar-style]** Theme `accent`/`muted` fallback semantics (corrected 2026-11, finding 024 — the former row's claim of value-aliases with `===` checks in the basic themes was wrong twice over): `===` NEVER holds in any theme — every slot is a separately constructed readonly `Color` instance, so identity comparison always fails and value comparison (hex string / `Color::equals`) is the only meaningful check. The value fallbacks differ per basic theme: `dark()` falls back on BOTH slots (`accent` #7091f5 = `primary`, `muted` #8b8fa8 = `secondary`); `light()` falls back on accent ONLY (`accent` #4f46e5 = `primary` while `muted` #6b7280 is an independent grey ≠ `secondary` #10b981); `ansi()` falls back on NEITHER (`primary` cyan 6 / `secondary` green 2 / `accent` magenta 5 / `muted` bright-black 8 are all distinct). The rich named themes (`dracula`, `tokyoNight`, `oneDark`, `githubDark`, `solarizedDark`, `solarizedLight`) use DISTINCT values per slot (e.g. dracula `primary` #bd93f9 ≠ `secondary` #50fa7b; `accent` #ff79c6 ≠ `muted` #6272a4). Never assume `accent` mirrors `primary` outside `dark()`/`light()`, never assume `muted` mirrors `secondary` outside `dark()`, and never compare slots with `===`. (Theme.php class docblock :37-38 still reads 'defaults to $secondary in basic themes' — stale for `light()`'s muted; left to the gated docblock pass, deliberately untouched here.)
- **[pattern:sugar-style]** Theme `adaptive()` reads the LAST `;`-separated field of `COLORFGBG` (so rxvt's 3-field form works) as an xterm-256 index and returns `light()` iff `Color::ansi256($i)->isDark()` is false — white 7/15 → light, black 0 and bright-black 8 (#7f7f7f) → dark. The old `$bg >= 8` rule inverted both; candy-code's `TerminalBackground::detect()` applies the same luminance rule.
- **[pattern:sugar-style]** Theme is the SSOT for theming across consumer libs (sugar-dashboard, sugar-charts). Any new colour-slot addition must be propagated to all named constructors — there is no default fallthrough; omitting a slot from a constructor leaves it at `\x00` (no colour).
- **[pattern:color-parse-named]** `Color::parse($name)` accepts 38 CSS/ANSI color names (black, red, green, yellow, blue, magenta, cyan, white, bright-* variants, purple/fuchsia/aqua/lime/maroon/olive/navy/teal/silver/gray/grey/orange/pink/brown/coral/gold/indigo/violet/turquoise/salmon/khaki/beige/ivory/lavender/plum/crimson/darkgreen). Case-insensitive, trims whitespace. Throws `InvalidArgumentException` for unknown names. Designed for user-facing color pickers where named colours are more ergonomic than hex codes.
- **[pattern:hsl-factory]** `Hsl::color($h, $s, $l)` uses CSS-style notation (hue 0-360, saturation/lightness 0-100) and delegates to `Color::hsl()` (which accepts 0-1 fractions internally). `Hsl::parse()` handles `hsl(...)` string input including `%` suffixes and whitespace — returns `null` on parse failure rather than throwing, which makes it safe for gradual colour-field enrichment.
- **[pattern:markup-tag-pair]** `Markup::parse($input, $defaultStyle)` parses `[tag]text[/]` syntax — distinct from `StyleParser`'s `[text](fg:red,bold)` format. The markup parser uses a style stack to support nested regions, and returns `list<Cell>` rather than a string, making it suitable for complex multi-style text layout at cell granularity. Unknown color names in tags are silently ignored (no exception).
- **[pattern:layout-spacing]** `Layout::joinHorizontalWithSpacing($pos, $spacing, ...$blocks)` and `Layout::joinVerticalWithSpacing($pos, $spacing, ...$blocks)` accept a `$spacing` parameter (null = no gap, int = gap in cells/rows). The spacing is inserted between blocks but not before the first or after the last. Use cases: dashboards with visible gutters, form layouts with field separators, log viewers with blank-line separation between entries.
- **[pattern:border-gradient-blend]** `BorderGradientBlend::fromColors(Color ...$colors)` accepts 1–5 colors and returns an object whose `sides()` method yields 4 interpolated colors (top / right / bottom / left) distributed proportionally around the perimeter. A single color produces four identical sides; 2–5 colors produce a clockwise gradient. The interpolation uses linear LERP via `Color::blend()`. Use when applying a multi-color border gradient via `Style::borderForegroundBlend()` (or the per-side `Style::border*Foreground()` setters).
- **[pattern:style-patch]** `Style::patch($other)` performs an incremental merge. Nullable slots (colours, width/height/max*, border, borderFg/Bg, marginBg, transform) apply only when non-null in `$other` — `foreground(null)` is skipped, not a clear — and a skipped prop's sentinel is NOT copied into the result's propsSet (a leaked sentinel would make a later `inherit()` refuse the parent's value). Every other prop applies whenever `$other` explicitly set it, zero/false included. Differs from `inherit()`, which takes the parent's value for anything the child hasn't set.
- **[exception:style-with]** `Style` uses `with()` instead of `mutate()` because it needs the sentinel-bool + `propsSet` tracking pattern: every setter passes `field: $val, fieldSet: true, propsAdded: ['field']` to track which properties the caller explicitly set. This allows `inherit()` to correctly take the parent's value only for properties the child hasn't explicitly set. See `sugar-core/src/Concerns/Mutable.php` for the standard trait; this exception is documented because the sentinel-bool pattern cannot be expressed via the simple array-merge mutate approach. Related naming mirror (registered 2026-11, finding 039): `Style::setString()` (:210, with the `of()` alias at :346 forwarding to it) keeps upstream's Go-style `SetString` spelling instead of this repo's `with*()`/bare-accessor grammar — a deliberate lipgloss mirror (its docblock cites `Mirrors lipgloss's SetString()`); the bound content slot reads back through `value()`.

- **[exception:tree-enumerator-default]** `Tree\Enumerator::default()` (`src/Tree/Enumerator.php:31`) carries the repo's forbidden `::default()` factory name and is an ACCEPTED, code-stamped exception: it mirrors `charmbracelet/lipgloss/tree.DefaultEnumerator` one-to-one, and the `rounded()`/`ascii()` presets alongside it cover the rest of the construction surface, so no `::new()` seam is wanted. Registered 2026-11 (finding 005) — never rename or flag its call sites on style grounds.

- **[gotcha:cassowary-solver]** `SUGARCRAFT_LAYOUT_SOLVER=cassowary` makes `SolverFactory::fromEnvironment()` return sugar-constraints's deprecated `CassowarySolver`, whose `solve()` now delegates wholly to `GreedySolver` (identical results, the old Ratio-returns-0 bug included as fixed) and raises `E_USER_DEPRECATED` per call; the factory raises a one-time `E_USER_DEPRECATED` naming the env var (deprecation, not warning: the opt-in changes no result, and a warning failed `failOnWarning` suites run with it set). There is no reason to select it. `SolverFactory::default()` survives the rename as a `@deprecated` forwarder to `fromEnvironment()` (dev-master consumers still call it) — migrate callers, never delete it.

- **[pattern:color-profile-semantics]** `Style::colorProfile()` mirrors charmbracelet/colorprofile's `Writer`: `Ascii` drops colour only (text attributes and OSC 8 survive, as `NO_COLOR` forbids colour, not emphasis); `NoTty` runs the finished render through `Ansi::strip()` so no escape — the style's own, pre-styled content's, a `transform()`'s or a border title's — reaches a non-terminal, while layout is kept. - **[pattern:bare-accessor-era]** sugar-style's bare-accessor conversion (2026-10-24) renamed only the two `get*` reads whose bare slots were free: `Style::defaultProfile()` (static ambient read; the `setDefaultProfile()` write is out of era scope) and `Style::borderSides()`, each keeping a one-line `@deprecated`/`REMOVED-IN: 2.0.0` forwarder. The other 31 `get*` accessors are blocked outright — every bare twin is a live fluent setter (`foreground()`, `width()`, `caps()`, …) and PHP admits one method per name; the owner ruling of 2026-10-24 settled them as permanent legal exceptions (next row), now rostered in `tests/BareAccessorEraTest.php` as `COLLIDER_EXCEPTIONS` with the era's discovery walk + sentinel fixture + bidirectional staleness + BC identity + README tie. Guard gotcha proven by mutation: an in-source sentence check must read the method's OWN reflection docblock, not a ±700-char source window — the neighbouring accessor's identical wording hides the deletion and the test stays green against a broken promise. 2026-11 follow-up (finding 012 governance trail, ST-36): the README's 'bare-accessor sweep landed' process prose was restructured into a Deprecated accessors section with a what-changed / call-this-now / removal triad — process narrative now lives in commits and this row, the README carries only the reader-facing contract.
- **[law:setter-collider-exception]** A bare-name collision with a fluent setter makes `get*` the legal permanent accessor (owner ruling 2026-10-24): PHP admits one method per name, so when `x(…): self` is the setter, the read `getX()` keeps its prefix forever — not renamed, not deprecated, no removal window. Documentation fleets that sweep bare accessors MUST carry an exception class in their guard, never an open "owner-pending" roster that silently rots once the ruling lands: the guard asserts each collider's canonical exception sentence sits in the accessor's own docblock, that it names the colliding setter, that the setter still exists fluent, and it fails closed on any disposition it does not recognize. See `sugar-style/tests/BareAccessorEraTest.php` (31 rows) for the first exception roster; the same-shaped get-prefix families elsewhere in the fleet fall under this law the same way — settle them into an exception class in their guards when their era lands, and never "fix" a collider getter without a fresh ruling.
